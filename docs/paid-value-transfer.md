# Prepared monetary transfer (initial execution path)

Default off. Do not set PAID_VALUE_TRANSFER_ENABLED=true until all web and webhook workers run this migration and end-to-end settlement, reversal and rolling deployment tests pass.

Supported candidate: one active verified cash or fully evidenced mixed cash/earned-credit one-off purchase (Stripe or PayPal; purchases made through the retired Plisio gateway can no longer be verified and are refused), same service lane, changing access to a new Stripe recurring agreement at a verified normal base or access-variant price. No multiple overlapping sources, unsupported currencies, recurring-to-recurring replacement, or operator grants. Existing identical-access carry is unchanged. A new verified first Stripe period is required. A fully discounted or fully credit-funded first invoice is supported only after a completed zero-amount Checkout, with a full discount, zero invoice balance, and saved payment method for subsequent renewals.

Preparation checks source and destination before checkout; settlement revalidates live payment and actual destination first billing term, freezes exact rational monetary value and FX evidence in the carry ledger, replaces old entitlement and grants the converted days in the same transaction. Existing reversal/return paths use the same carry ledger. Unexpected evidence fails closed. No new refunds or provider mutations occur. Round up once to whole service days; no monetary rounding before conversion.

This is a scoped initial implementation, not a claim of full upgrade/downgrade support. Review database and provider-specific regression coverage before enabling.

Same-access purchases with a different recorded currency must also use monetary valuation rather than copying days one-for-one. A completed transfer acknowledges replays without resurrecting reversed value. The receiving Stripe checkout and first invoice must both attest the same verified amount and currency (including zero for a fully funded or discounted first period); mixed receiving Stripe checkouts can also settle their exact earned-credit reservation atomically with the paid transfer. The existing provider minimum applies to nonzero cash payments; a missing or underfunded reservation rolls back all local entitlement changes. For a mixed-funded source, its redeemed credit and provider-paid cash remain separate exact fractions in both currencies. The existing source-payment-loss policy reverses that purchase's transferred service; no provider cash refund can include earned credit, and the transfer creates no new credit or debit. Full-credit source purchases follow the separately verified redemption-ledger path below.

New full service-credit redemptions freeze their original commercial terms and can be valued as a source for supported Stripe transfers using their exact redemption debit and complete funding allocations. No provider cash is attributed to that source. Historical redemptions without frozen terms are not automatically transferred.

## Release checklist

Before enabling the flag, deploy all web and webhook workers on the same tested version, run the production deployment acceptance audit, and verify positive and zero-amount Stripe checkouts in a test-mode account, including subsequent renewal, failed settlement, duplicate webhook, and source/target refund handling. Keep the feature off if any acceptance check fails. Existing recurring-to-recurring currency replacements and histories without verifiable terms remain outside this implementation.

Existing Stripe recurring agreements cannot be changed to another currency in-place. A customer who explicitly stops renewal can record the desired target currency and price; the worker verifies that the paid period has elapsed and the old Stripe agreement is terminal before requesting fresh authorization. The exact new Stripe price must settle before the change is marked applied. No new provider payment is initiated without the customer's checkout. This is not an immediate cross-currency replacement.
